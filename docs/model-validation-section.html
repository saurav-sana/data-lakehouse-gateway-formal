4. Model Validation Suite & TLC Configuration

The gateway's coordination protocol is written as a PlusCal specification and model-checked with TLC. Instead of testing individual code paths, the checker explores every interleaving of clients, workers, the lease manager, the ETL committer, the garbage collector and injected faults, within fixed bounds. If any interleaving breaks a property, TLC returns a step-by-step counterexample.

A. Why a Formal Model, and How It Runs

The riskiest behaviours here are concurrency bugs: a zombie worker publishing after losing its lease, a cache entry surviving a snapshot commit, a blob freed while a client still holds it. They depend on rare orderings that unit and load tests seldom hit.

  1. Model
    Each component (client, worker, lease manager, ETL, GC, evictor) is a PlusCal process over shared state.
  2. Inject faults
    Worker crashes and lease timeouts that create zombie workers happen nondeterministically, within a budget.
  3. Explore & check
    TLC enumerates all reachable states and checks every property in each one.

C. Safety Invariants

A safety invariant must hold in every reachable state. They answer "can anything go wrong?"

Tenant isolation & authorization

Keeps one tenant's data and identity out of another's.

  • TenantBinding: admitted jobs carry the tenant and security context from verified auth, never the payload.
  • MismatchRejected & UnauthorizedIsInert: a tenant mismatch ends in UNAUTHORIZED, with no queue entry, blob, commit or delivery.
  • RLSEnforcement: once RUNNING or later, the row-level-security predicate was applied for the authenticated tenant.
  • TenantIsolation: a delivered result carries the receiving client's tenant, query and context.
Result, claim-check & cache integrity

Keeps a pointer from resolving to wrong or missing data.

  • DeliveredResultIntegrity & ClaimCheckIntegrity: held results point at an existing, published blob matching tenant, query, context and version.
  • BlobPtrIffResultState: a job has a blob pointer exactly when it has a result.
  • NoSharedBlobPointer & BlobPoolConsistency: no double allocation, no leaked blobs.
  • StagedBlobWellFormed: staged blobs record writer and lease epoch, so the GC can spot orphans.
  • CacheIntegrity & CacheFreshness: cache entries match their own key, and only the current snapshot is cached.
Job, lease & queue discipline

Keeps a request from being lost, duplicated or double-run.

  • ExactlyOnceCommit: at most one commit, and COMPLETED holds exactly when it committed.
  • FailedImpliesExhausted: FAILED only after every retry is spent.
  • LeaseOwnership & QueueConsistency: only active jobs have an owner, and a QUEUED job is in the queue exactly once.
  • FlightIsLocal: Flight requests are never queued, leased or retried.
  • SnapshotBound & TypeOK: no snapshot newer than the catalog's, and all state stays in its declared domain.

D. Transition and Temporal Properties

Transition properties

Constrain which steps may ever happen.

  • EpochMonotonic (\(\Box[\,\text{epoch}' \ge \text{epoch}\,]\)): lease epochs never decrease. This fencing-token guarantee makes zombie workers harmless.
  • SnapshotNeverChanges: a job keeps the snapshot it was bound to (snapshot isolation).
  • CatalogMonotonic, CommitMonotonic, DeliveryImmutable: snapshots only advance, commit counts never fall, delivered results never change.
  • TerminalAbsorbing: COMPLETED, FAILED and UNAUTHORIZED are final.
Liveness properties

Require progress. Checked under weak fairness of all background actors, with crashes and timeouts bounded.

  • LiveTermination (\(\text{Pending} \leadsto \text{Terminal}\)): every queued or running request reaches COMPLETED, FAILED or UNAUTHORIZED. With FailedImpliesExhausted, work cannot hang and cannot fail early.
  • ClientsComplete (\(\forall r:\ \Diamond\,\text{released}_r\)): every client eventually releases its result.
  • GCReclaimsGarbage (\(b \in \text{GCable} \leadsto b \notin \text{GCable}\)): orphaned and unreferenced blobs are eventually reclaimed.

E. Assumptions the Guarantees Rest On

  • Trusted identity: tenant and security context come from a trusted verifier such as a signed JWT; the payload tenant is untrusted and contexts don't change mid-request.
  • Atomic job records: the job store supports compare-and-set on state, owner and lease epoch. Every fence depends on it.
  • Immutable results: published blobs are immutable and publication is atomic.
  • Fault model: fail-stop crashes and bounded lease timeouts only. No Byzantine faults, clock skew or message loss.
  • Reliable queue: FIFO, with no loss or duplicate delivery.
  • Replacement workers: start only after the crashed worker's leases are reclaimed.
  • Flight is in-VM by design: admission and execution share one VM, so no network boundary is crossed for data transfer. That is why Flight has no queue, lease, fence or crash window; a VM crash is a dropped connection and the client retries. Flight results skip the shared cache by default.
  • Abstractions: snapshots are per-tenant integers, queries are opaque IDs, cache identity is exact-match, and RLS is a flag set at execution. The model doesn't check the SQL rewriting itself.

F. Design Gaps Found by Static Formal Analysis

Reviewing the specification and its first model revisions exposed these gaps. Each became a concrete design requirement.

1CacheInvalidation off by one. A stale snapshot's result stayed servable for one more commit.Invalidate every entry at or below the old snapshot atomically with the snapshot advance.
2StorageDelivered blobs never reclaimed. Job and client references never expired, so the pool leaks and the earlier "GC fix" was inert.Define result lifetime with a client release or TTL, and let the GC reclaim released blobs.

4LivenessUnconditional lease expiry. Any job could be expired at any time, so "every job terminates" held vacuously by ending in FAILED.Expire a lease only on owner death or heartbeat timeout; allow FAILED only after retries are exhausted.
5SecurityCache key ignored security context. A second context overwrote the first, causing thrashing and weak isolation.Include the security context in the cache key.
6StorageWrite and publish were one atomic step. The model could not produce the real failure: a zombie writes a blob, fails the epoch fence and leaves an orphan.Write a staged blob recording writer and epoch, then publish the pointer under a fenced compare-and-set.
7StorageGC couldn't tell in-flight from orphaned. Freeing a staged blob a live worker is about to publish would corrupt results.Reclaim a staged blob only once the job's lease epoch has moved past the blob's epoch.
8CacheCache population races with release and GC. An entry could point at a freed or reused blob.Re-verify blob existence and metadata atomically on insert, or use a conditional put.
9CacheCache entries pin blobs with no eviction. A full pool can starve new jobs.Add TTL or LRU eviction and a pool-pressure policy.
10LivenessWorker recovery before lease reclaim. Jobs stay CLAIMED with no actor left to advance them.Reclaim leases before a replacement starts, or give workers an incarnation number.
11CacheCommit and cache write were one step. Real systems can crash between them, leaving a job COMPLETED but uncached.Treat the result cache as best-effort; never assume an entry exists after COMPLETED.
12ContractFreshness contract was unstated. A request admitted before an ETL commit legitimately returns the older snapshot.Document snapshot isolation at admission: results match the bound snapshot, not necessarily the latest.
13ContractFlight has no fencing or recovery by design. A VM crash mid-execution has no gateway-side recovery.State that Flight failure means client retry.

G. Out of Scope for This Iteration

  • Permission revocation and policy-version changes
  • Snapshot expiry while a job is bound
  • Single-flight coalescing of identical queries
  • Real clock-based TTLs and heartbeats
  • VM-level crashes on the Flight path
